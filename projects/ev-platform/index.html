02Bronze

Every source version is kept as delivered, and nothing is reloaded unless its content changed

Sources overwrite themselves, so Bronze is the only place their history survives. Each version is stored as Parquet and as text rows in PostgreSQL, with one row in the ingestion ledger bronze.source_files.

03Silver

Silver cleans, historises and links the sources in ten SQL models, each rebuilt only when its inputs change

05Scheduling · Airflow

Two DAGs split by how often a source changes; the daily run takes about 11 minutes and skips what is unchanged

Boundaries change once per ASGS edition, chargers and prices daily. A rarely changing reference load has a different schedule and failure impact, so it is its own DAG, linked to the daily one by an Airflow Asset.

06Data operations dashboard

One data workspace answers whether today's data can be trusted, where it came from, and what it shows

A small Flask app on the same database (port 8790) for the people who own the data: run-level data quality, table profiling, full lineage, the dictionary and the BI report. It is read-only except for the dictionary.

6.1Data quality · run gate

26 checks in seven dimensions run at the end of every ev_sources run and are appended to meta.data_quality_result before the gate decides, so failed runs are on record too.

SeverityEffectExample
errorFails the run, fires DataQualityErrorCharger without an SA4 region; DC augmentation below 50%
warnReported, run continuesOperator spelling not in the dictionary
infoMeasured, describes the data73% of TfNSW rows have no station name
Gate passedLatest run, 6 Oct 2026 · 0 blocking errors · 3 warnings

The gate failed once, on 29 Sep: DC augmentation was below the 50% target until the Evie source was added. Coverage is now 56.4%.

6.2Table data quality · profiling

Rule checks say whether a run may publish; a profile says what is actually in a table. Any table or view can be profiled on demand from one read-only snapshot, next to the rule checks that cover it.

6.3Full data lineage

Every Airflow task declares the tables it reads and writes; the same declarations go to Marquez as OpenLineage events, and a test fails if a model's SQL touches a table it did not declare. Gold views and the screens that read them come from PostgreSQL's dependency catalog and the apps' queries.

07Job operations dashboard · Grafana

Grafana and Slack alerts tell the operator when a run, a source or the stream goes wrong, before a user notices

Airflow sends StatsD metrics; a small exporter reads the data's own state from PostgreSQL every 60 s (freshness, volume, quality, model age, stream lag). Prometheus evaluates the alert rules and Alertmanager posts to Slack.

AAppendix · Design decisions

The trade-offs behind the platform

Each choice is written up as a decision record in docs/decisions/.

Detect change before downloading

ProblemDaily runs should not re-store or re-process identical data.

ChoicePer-source checks: CKAN last_modified, HTTP 304 for ABS, SHA-256 for snapshots. Unchanged models are skipped too.

Rejected: trusting the portal's "Last Updated", which changed while the bytes did not.

DAGs split by change frequency

ProblemBoundaries change yearly, chargers daily.

ChoiceA manual reference DAG and a daily DAG linked by an Airflow Asset. Initial and incremental loads are the same idempotent run.

Rejected: a separate initial-load DAG that would drift from the daily logic.

Record linkage in SQL

ProblemTfNSW and OCM share no key and spell operators differently.

ChoiceDC-capable OCM site within 300 m; beyond 50 m the operator or address (trigram) must agree.

Rejected: substring operator matching, which paired unrelated operators.

Operator data where the open registry falls short

ProblemOpen Charge Map covered 41.8% of DC chargers, under the 50% target.

ChoiceEvie's own site data, matched only to TfNSW chargers of the same operator; Evie wins where both match. Coverage rose to 56.4%.

Rejected: loosening the OCM rules, which only paired chargers with other operators' sites.

A model proposes, a person decides

ProblemSpellings like GET Electric defeat the rules.

ChoiceLangChain sends unregistered spellings to an OpenAI model with structured output; a person accepts or rejects on the screen or in Slack.

Rejected: calling the model inside the daily pipeline, where a wrong answer would merge two operators unseen.

The stream lands, the batch decides

ProblemPrices change between daily runs.

ChoiceKafka + Spark land OCM change events in Bronze with exactly-once sinks; the history model stays the only writer of the SCD2 table.

Rejected: the stream merging into the history itself, racing the batch.
